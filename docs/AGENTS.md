# Documentation rules

These rules specialize the repository contract for `docs/`.

- Write public technical documentation in concise English and learning walkthroughs for the user in clear Persian.
- Explain purpose and behavior before implementation detail. Define unfamiliar terms on first use.
- Keep one source of truth: link to a canonical document instead of copying large sections across files.
- Use Mermaid only when relationships or sequences are materially clearer than prose.
- An ADR contains status, date, context, decision, alternatives considered, and consequences. Never rewrite accepted history to hide a changed decision; supersede it.
- A sprint plan contains goal, demonstrable user outcome, in/out scope, work breakdown, risks, evaluation, and Definition of Done.
- A sprint review records delivered behavior, architecture/data flow, meaningful challenges, decisions, validation evidence, limitations, and follow-up work.
- A Persian learning walkthrough explains backend and AI concepts step by step, includes one traced request, common failure modes, and a short glossary.
- Update commands, paths, configuration names, diagrams, and API examples whenever code changes them.
- Do not document planned behavior as already implemented. Label proposals, baselines, measured results, and known gaps precisely.
